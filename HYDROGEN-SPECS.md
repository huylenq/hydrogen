# Hydrogen functional customizations

This file records intentional behavior in Hydrogen, Huy's fork of T3 Code, that must survive upstream merges and refactors. It states what each feature must keep doing, not how it is built: exact keys, sizes, file names, and copy live in the code, tests, and linked user docs. Carry these requirements into whatever implementation upstream changes force.

## Upstream runtime compatibility

The unmodified upstream mobile client must be able to use this server. Do not add fork-only values to, or change the meaning of, shared runtime contracts or persisted thread/session state (runtime modes, approval policies, sandbox mappings and their defaults). Lexicon and Hermes must not add thread runtime modes or alter upstream approval behavior. Keep local data repairs out of the shipped migration history.

## Rebrand

The fork presents itself as Hydrogen: the web and desktop app name (`APP_BASE_NAME` in web and desktop branding, so window titles, menus, and About), the sidebar brand (a heavy "H₂" mark, `HydrogenMark`, drawn to match upstream's T3 wordmark, with no text label; `customizations/huy/HydrogenSidebarBrand.tsx` centers it on the sidebar unless the environment pill is shown, without raising the measured minimum sidebar width), the page title and boot splash label, the dev launcher's macOS bundle (`Hydrogen (Dev).app`), and the macOS permission helper, which names the running bundle as System Settings lists it. Labels and app artwork change. App icons use the sidebar’s H₂ mark across desktop, web favicons and splash, and fork-built mobile launcher, splash, monochrome, and notification assets. Preserve the development blueprint, nightly sky, and production black backgrounds, including the macOS safe area. The macOS export frames the native artwork with scripted 100px transparent margins and a soft shadow, so it works without the newer GUI export preset. The Icon Composer projects and exports are maintained together; see [Brand icons](assets/README.md) for generation and verification. Everything upstream or the user's data depends on keeps its T3 name: package scopes (`@t3tools/*`), the `t3` CLI, `t3_*` MCP tool names, MCP/OAuth/provider client identities, protocol schemes, bundle IDs, `T3CODE_*` env vars, T3 home (`~/.t3`), Electron profile folders, and `productName` (packaged app and updater). Electron's runtime name (`app.setName`) stays `T3 Code <stage>` because macOS Safe Storage keys its keychain item by it; renaming it would orphan encrypted secrets and cookies. Hardcoded "T3 Code" copy elsewhere, including copy that upstream tests assert, is left as upstream wrote it to keep merges cheap.

Known limitation: packaged builds show both names. Finder, the Dock, the bold app menu, and the installed bundle (`T3 Code (Alpha).app`) come from `productName` and the runtime name, so they say "T3 Code", while window titles, menu items, and About say Hydrogen. Renaming `productName` would change the install path and the updater identity, which this rebrand does not touch. The dev build is unaffected because the dev launcher names its own bundle `Hydrogen (Dev).app`.

## Desktop app location

On macOS the desktop app records its own `.app` bundle in `desktop-app.json` (`{"version":1,"appPath":…,"development":…}`) in its state directory, the same directory the app control socket address is derived from, each time it starts. Lexicon reads it to launch Hydrogen when the socket is not answering, so it never assumes a checkout path or `/Applications`. A development bundle only works while its dev runner serves the renderer, so Lexicon asks for `vp run dev:desktop` in that checkout instead of launching it. The file is replaced atomically and is fork-only; upstream ignores it.

## Project move

`t3 project move <project> <path>` repoints a project at its moved checkout and keeps its threads. It sends `project.update` with the new `workspaceRoot`, which the server already supports, through the running server like the other `t3 project` commands. The project may be named by id or by its stored path; a stored path whose directory is gone is matched after resolving `~`, relative segments, and trailing slashes. The server refuses a path that another active project already uses. Linked worktrees keep pointing at the old `.git` until `git worktree repair` runs in the new checkout, which the command reminds you of. For the desktop dev state, run it from the checkout with `VITE_DEV_SERVER_URL` set and no `--base-dir`, so it targets `~/.t3/dev`.

## Vim navigation

Opt-in modal keyboard profile for web and desktop (not native mobile). Full command set: [Vim navigation](docs/user/modal-keyboard.md).

- Normal mode shows which surface has focus; no persistent mode/status strip.
- Escape leaves the composer for Normal mode (open pickers/overlays handle Escape first). Submitting from the keyboard returns to navigation without stealing focus the user already moved.
- Picking a model or effort from Normal mode stays in Normal mode and restores the prior focus.
- Text inputs, embedded editors, and terminals keep their own editing keys; terminals have an escape hatch back to navigation.
- Focus and mode survive pickers, thread switches, and leaving/returning to the app window. Returning to the window never focuses the composer by itself.
- Each command runs exactly once; help, settings copy, and behavior agree.
- `hjkl` mean something within each area; bare `h`/`l` never move focus between areas. `H`/`L` (and `w h`/`w l`) step between the sidebar, the main area, and the right panel (opening it when hidden), stopping at the outer edges. Right-panel tabs stop at both ends.
- `Space` does what `j` does and `Shift+Space` what `k` does, so tapping Space reads on. Space does not focus the right panel; `L` or `w l` does.
- Bare digits are not Normal-mode app keys: upstream's `mod+1`–`mod+9` select threads, the diff uses digits for fold levels, and a focused pending question takes `1`–`9` for answers.
- Conversation reading motions move the reading cursor: `j`/`k` by block (each top-level paragraph, heading, table, code block, and list item of an answer, then the header and each visible folder and file row of the answer's changed-files card; every other timeline row is one block), `[[`/`]]` by section (message starts, headings, blocks opening in bold, and changed-files card headers; like Vim's section motions), `J`/`K` by user message. Moving back from partway through a unit returns to its start first, and holding any of these keeps stepping.
- The cursor lives in a band clear of the outer fifth at each end of the readable area, like Vim's `scrolloff`, and the page stays still while it moves within the band (half a line of slack), so most steps do not scroll. A step that would leave the band on the side it is heading scrolls before the cursor reaches the edge: continuing down lands the target's top on the band's top line, continuing up lands its bottom on the band's bottom line. A step that reverses direction only brings its target into the band, keeping the block just left in view. Section and message jumps land on the band's top line. Scrolling by hand during a landing stops it where the user leaves the view and starts a fresh read. `j` pages half a screen through a block that runs past the bottom edge. Block steps and pages glide calmly, around half a second, so the eye can follow; section and message jumps stay quick. Reduced motion makes both instant. The readable area is measured against the composer as it is drawn, so a collapsed composer does not cause early scrolls.
- The reading cursor shows as a bar in the gutter left of the text (at the text column's edge for answer blocks, list items included; beside the row otherwise) plus a faint tint over its block. On a user message it highlights the bubble's border instead (no bar, no tint). As a landing starts the tint brightens briefly, or a user message's border flashes twice, so the eye can follow the block to its new spot. Every `[[`/`]]` stop, scrolled to or not, shows why it is a section: its heading or bold lead highlights briefly like a cited quote (a user message flashes its border; a plain message start pulses). Without a cursor, the first `j` shows it on the first block starting on screen and the first `k` on the last block ending on screen, without scrolling. The exception is `j` while the latest answer has begun on screen or above it and the cursor has not been on it: it starts at the answer's beginning (the latest turn's first assistant message outside an open turn fold), landing it on the band's top line when it is above the screen. Once the cursor has been on that answer or past it, the screen rule applies again; a thread switch forgets this. Scrolling the cursor fully off screen hides it and drops it. Clicking in the conversation puts the cursor on the block under the pointer (the nearest block when between an answer's blocks) without scrolling or a landing cue; a drag that selects text leaves it alone.
- `Ctrl+j`/`Ctrl+k` scroll the conversation smoothly, and holding them glides continuously. Any other scroll interrupts the glide. Reduced motion jumps instead. `gg`/`G` jump instantly to the conversation's start or end and put the reading cursor on its first or last block with the landing cue, so reading goes on from there like Vim. Any keybinding on these chords wins, whatever its `when` clause; off macOS that includes the default `mod+j`/`mod+k`.
- `zt`/`zz`/`zb` scroll like Vim's: the cursor's block top lands just inside the top of the readable area (a twentieth of it clear, outside the band), its middle at the middle, or its bottom just inside the bottom. They glide quickly with the landing cue, keep the cursor, and without one place the block where reading starts on screen.
- `z i` toggles the reading lamp (like Vim's `zi` view toggle), which shows the cursor by dimming the rest of the conversation instead of tinting it. The lamp always lights a block, following the screen when the cursor scrolls away. It is static (no animation), persists per client, and applies only while Vim navigation is on.
- In a changed-files card `h`/`l` work like a file tree: `l` opens a file's diff (or the header's full diff), expands a collapsed folder, or steps into an expanded one; `h` collapses an expanded folder or steps out to the enclosing folder, then the header. Steps scroll only as far as needed. A turn fold ("Worked for …") and a tool group ("Ran 3 commands") work the same way: `l` expands one or, once open, steps into the first row it reveals; `h` collapses it. An expanded tool group's calls are stops of their own (`j`/`k` walk them, tracked by list index through the group's virtualized, recycling list, which scrolls to keep the cursor's call clear of its edge fades and renders a neighbor call it has not drawn yet instead of letting `j`/`k` skip past it; scrolling the group by hand until the call is out of its view drops the cursor); `l`/`h` open and close a call's output, and `h` on a closed call steps out to its group header (the calls row names its header; it is not assumed to be the row above). A lone tool call opens and closes its output in place. `h` from any row an open turn fold reveals (including that row's changed-files header) steps back out to the fold. Fold membership is computed when timeline rows are built (`turnFoldRunId`), not guessed from the DOM. Changed files and folders are known to the cursor by path, so opening or closing a folder above it keeps it on the same file. Elsewhere `h`/`l` in the conversation show a hint instead. `Enter` clicks what the cursor is on in a card (file, folder toggle, header's full diff) or toggles a turn fold, tool group, or tool call; anywhere else in a conversation `Enter` still focuses the composer. A stuck (sticky) card header is measured at its unstuck spot, so landings don't chase it.
- An HTML render is one reading block. `Enter` on it focuses its frame; an Escape the page leaves alone returns focus to the surface around it (conversation or right panel) with the reading cursor on the render's block (`releaseEmbeddedFocus`). With Vim off, that Escape just releases the frame's focus.
- `c` cites the cursor's block through the regular citation flow (same capture as a mouse selection, comment editor beside the block, Escape removes the citation). Only answer text is citable.
- The review diff (`DiffPanel`) is a Vim surface after Huy's evil-magit setup. Its keymap is layered over the app's (`layerModalBindings`): diff keys win, and app sequences they don't shadow keep working (`w h`, `H`/`L`, `q`). Diff keys work from anywhere in the diff panel (toolbar buttons, loading state, viewer); text fields keep their keys and buttons keep Enter/Space. Right-panel focus is an intent, not a one-shot (`panelFocus`): `r`/`w l` focus the content's best focus anchor (the viewer, else the panel), and if the lazily loaded panel or its viewer mounts later, it takes focus then, unless the reader clicked or moved focus out first. Once a diff anchor has focus, the panel keeps it across viewer remounts (collapse all, scope switch, refresh). The cursor is Pierre's line selection, or a gutter bar on a file header; the first motion, or one after the cursor scrolled off screen, shows it on the first line on screen. Motions: `j`/`k` by line through headers; `Ctrl+j`/`Ctrl+k` by file header or hunk start; `]`/`[` (not `gj`/`gk`) by sibling hunk, or file to file from a header; `^`/`g h` to the header; `h`/`l` switch columns in split view, otherwise step to the header, then collapse/expand or enter. `Space`/`Shift+Space` and `Ctrl+f`/`Ctrl+b` scroll a page (magit's diff, not the app's Space = `j`), `Ctrl+d`/`Ctrl+u` half a page. `Tab`/`Shift+Tab` fold the file/all files. Digits are magit's section levels: `1`/`2` act on the cursor's file and `Alt+1`/`Alt+2` on every file (magit's `M-1`/`M-2`); level 1 is the header and 2 shows it all. Pierre cannot fold single hunks, so a diff has no level 3 or 4 (in magit's own diff buffer they match level 3 anyway). `+` grows the context around every gap in the file. `/` searches lines and file paths with smartcase, wraps, and opens a collapsed file it lands in; `n`/`N` repeat. `v`/`V` start a line selection within one file, `y` copies it; `y y` copies the line, `y s` the hunk (header: path); `c` comments on the line or selection, and the cursor rests on it after the comment closes. `Enter` opens the file at the cursor's new-file line; `g r` refreshes. Escape ends a selection first, then focuses the conversation. `?` or the toolbar's keyboard button (shown while Vim mode is on) opens a cheatsheet of the diff's keys grouped by task (`DIFF_VIM_CHEATSHEET`, which must list every diff command). Rows mirror Pierre's own layout (`diffRows`, checked against its `iterateOverDiff`), including expanded context read from the viewer. That read uses two protected Pierre fields (`CodeView.idToItem`, `hunksRenderer.getExpandedHunksMap` in `expansionsOf`), so it reaches files scrolled out of the window; after a `@pierre/diffs` upgrade, run `diffVimRows.test.ts` (parity with `iterateOverDiff`) and press `+` then `j` in a diff, since a moved field throws on the first motion. The Pull Requests code tab does not have this yet.
- Diff files read as cards in every diff viewer (`StyledDiffCodeView`: the review diff and the Pull Requests code tab): an 8px gap between files and around the list, a raised sticky header band with a hairline under it, a rounded hairline ring, and a card surface that pops off the app background: the theme's `--card`, lifted a little further in dark themes. The card becomes each file's `--code-background`, so gutter and change tints follow it. The file holding the Vim cursor (line or header) is highlighted as a whole, like magit's section at point: a 2px outline and a header band tinted in the cursor's accent (`--diffs-modified-base`), driven by a hidden `data-diff-active-file` marker in its header prefix. Hidden context between hunks reads as the card torn open: a strip of the panel background with parallel zigzag edges and the unmodified-line count centered, in place of the shared viewer's hairline rule (fork CSS in `diffFileCards.ts`, within the separator's fixed height). It lives in `customizations/huy/diffFileCards.{ts,css}`; the shared viewer only imports its layout and shadow-root CSS. Spacing must go through Pierre's `layout` (its virtual layout counts it) and the card edge must stay paint-only (outline, not border or margin), or scroll positions drift.
- `g k` opens the commit dialog from any chat view. Upstream mounts git actions only inside the thread details card, so with the card closed `g k` opens it, and its git actions open the dialog once git status loads (`commitDialogRequest`). The card stays open afterwards: it shows the commit's progress and hosts the default-branch prompt. The request lives only while the card's git actions for that thread stay mounted: closing the card or leaving the thread before status loads cancels it, while the card moving between popover and inline keeps it. When committing is unavailable (clean worktree, git action running), `g k` says why instead of reporting the command unavailable.
- The commit dialog is a magit-status-style file list (`useCommitFileListKeys`), 768px wide with a 12px mono file list that grows to half the window before scrolling. In Vim mode it opens with focus on the list: `j`/`k` (and arrows) move a cursor that follows its file by path across status refreshes, `Space` includes/excludes the file, `Enter` opens it in the editor, and `i` edits the message. `Esc` in the message returns to the list; `Esc` on the list closes the dialog. `Mod+Enter` commits from anywhere in the dialog (blank message auto-generates). The list is a multi-select listbox (selected = included) whose active option follows the cursor, so screen readers track it. With Vim off, the list keys and `Mod+Enter` still work, but focus and `Esc` keep upstream's behavior.

## Flow

Web and desktop focus mode for working through threads that need attention.

- Sessions can be flagged as important with Vim Normal-mode `t f` (bare `f` remains the find prefix). It toggles the focused Flow bar card or overview session, including snoozed chips; in a conversation it toggles the open existing thread. Repeating removes the flag. Important sessions use a warm metallic gold palette for borders and titles, a very faint background tint, and matching navigation and keyboard focus outlines on both Flow surfaces while their status colors stay readable. In the Flow bar, the currently open important session has a solid gold border, a stronger gold background, and an inset gold stripe along its left edge so it remains distinct from other important sessions even while focus is elsewhere; this treatment does not change card geometry or title weight. Flags persist per client across reloads, keyed by environment and thread, independently of pinning, settlement, and Flow mode. Important sessions lead the waiting queue and working previews, preserving the existing time order within each priority; unflagging restores ordinary ordering. Keyboard focus stays on the same session when priority changes move its card. Help names the target and offers the reverse action. Verification: [`Flow.logic.test.ts`](apps/web/src/components/Flow.logic.test.ts), [`useFlowAutoJump.test.tsx`](apps/web/src/hooks/useFlowAutoJump.test.tsx), and [`ModalKeyboard.importance.test.tsx`](apps/web/src/components/ModalKeyboard.importance.test.tsx).
- Vim Normal-mode `s` snoozes the focused Flow preview, bar card, or the open existing thread through the same quick-duration dialog and mutations as the sidebar. It captures the selected environment and thread before the dialog takes focus, so it never snoozes an unrelated route hidden behind the overview. On a focused snoozed chip it wakes that session. Server capability, permission, and blocked-work restrictions still apply. Verification: [`ModalKeyboard.importance.test.tsx`](apps/web/src/components/ModalKeyboard.importance.test.tsx) and [`threadSnoozeCommand.test.ts`](apps/web/src/customizations/huy/threadSnoozeCommand.test.ts).
- A Flow bar of waiting threads (important first, oldest first within each priority) and the Flow overview, a grid of running-session previews shown when nothing waits. Subagent threads are excluded, as in the sidebar; their parent session carries their activity. Opening a session from the overview keeps Flow on and does not reveal the sidebar; Escape from an inspected session returns to the overview.
- The Flow bar's working-session bench (right end, beside the queue cards) is a glance at the workload while working the queue, not a detail surface; the overview tiles carry the detail. Each session is a one-line chip (favicon and title, truncated; no status mark) in a three-row grid filled column by column, important first and newest-created first within each priority, with columns sized to their widest chip up to 300px (a single column shrinks to fit a narrower bench), so up to three sessions take one column; the columns sit at the right edge. It takes at most half the bar while queue cards show and the full width otherwise. Column capacity uses those content widths, adding another column whenever it fits before collapsing sessions into a final "+N more" chip that opens the overview like `w g`. Hovering a chip shows its full title and project. The bar, bench included, is absent while the overview shows. Sizing and overflow coverage: [`Flow.logic.test.ts`](apps/web/src/components/Flow.logic.test.ts).
- `flow.overview.toggle` (Vim `w g`, no default modified shortcut) holds the overview open even while threads wait, enabling Flow if needed. Waiting threads lead the grid with their status, and Flow doesn't enter them on its own. Opening any session releases the hold (no "Back to previews", Escape doesn't return to the grid); with threads waiting, only `w g` brings the overview back. Escape returns an opened session to the overview only when nothing waits, so it never jumps into the queue. Disabling Flow releases the hold too.
- The overview lays out balanced, equal-width rows, preferring the squarest grid of full-width cards (columns never fewer than rows; a narrow pane stacks more rows of full-width cards), and widens into more, narrower columns (down to a readable minimum) only when those rows would overflow the pane height, measured with the tallest card (subagent lines make cards taller); it supports spatial Vim navigation; grid edges are hard stops (`h` at the left edge does not enter the sidebar). Working-session positions stay stable as activity updates arrive; important sessions lead, then creation time sorts each priority newest first.
- At the bottom of the overview (also under the empty-state message), a single unlabeled, muted line (`FlowSnoozedRow`, never wraps; chip titles truncate to fit) lists every snoozed thread as a chip, soonest wake first: favicon, title, a static dot while running, and the wake countdown. Vim grid motions reach chips like tiles (`j` from the bottom tiles drops to the nearest chip; Enter opens), but snoozed threads stay off the conveyor, Flow bar, and number keys. A chip opens the thread exactly like a sidebar click while Flow is on (no wake).
- Overview tiles (`FlowSessionPreview`) show a two-line-tall project favicon beside the title and, under it at the same indent, one line with the project on the left and provider icon, model, and effort right-aligned. The model drops a brand prefix the icon already shows (`stripIconRedundantModelPrefix`: "Claude" under the Claude icon, "Grok" under Grok); harnesses whose icon isn't the model brand (Cursor, OpenCode, Codex's GPT) keep the full name. The body shows the latest messages as markdown, headed by the latest user message in a compact, full-width prompt strip with left-aligned text, pinned at the top of the preview body below the header. The strip uses modest inner padding and tight line spacing, small corners, a muted message tint, and a pronounced outer shadow cast downward below the bubble; this treatment applies only to the Flow grid on web and desktop, leaving main chat bubbles unchanged. The strip stays at that top position as replies grow or scroll; the replies use the remaining height beneath it, with no role labels. A prompt longer than two lines clips to its first two without dimming the visible text. Replies disappear at the strip's bottom edge, beneath its outer shadow. Verification seam: [`PromptBubble`](apps/web/src/components/FlowSessionPreview.tsx). Recent tool activity stays pinned at the bottom of the tile body, outside the replies' scroll area, with the replies using the space between the prompt and tool stack. The stack uses message size and the main chat's settled labels (a shell call shows its command). While the session is Working, the tile takes its live row from the chat's own row derivation (`deriveMessagesTimelineRows`): the live tool row shines, and when the chat would show Thinking, a "Thinking" row with its sweeping highlight follows the activity. On a Monitoring tile, that row instead shows the background work the turn left running, titled as in the chat's composer banner ("Waiting on subagent …", "Running: …"); it sweeps only when the work will wake the agent. Subagents the footer below lists are left out of that row; one it can't show yet (detail not loaded or no matching entry) stays.
- Above each overview tile on web and desktop, outside its frame and click target, a muted heading line ([`FlowSessionCheckoutStrip`](apps/web/src/customizations/huy/FlowSessionCheckoutStrip.tsx)) shows the thread's branch, a worktree icon (full path on hover) when it runs in a worktree rather than the main checkout, and on the right its pull request as state icon, `#number`, and state in the sidebar's PR colors. It keeps the former footer's overlay styling, line height, and gap from the card. Both the heading and subagent footer have a small, matching left and right inset to align optically with the card's rounded corners. Clicking the PR opens it in the browser (honoring the link-target setting) without opening the session. The line keeps its height when empty so grid rows stay aligned.
- Below each tile, still outside its frame, each of the session's working subagents (queued, running, or waiting, provider-native or app-owned) gets one footer line ([`FlowSubagentFooter`](apps/web/src/customizations/huy/FlowSubagentFooter.tsx)) in the heading's box (`FLOW_FOOTER_LINE_CLASS`, same height): the chat's round provider avatar shrunk to 16px (no status dot, since every listed subagent is working), the title, a dot, the progress line, and elapsed time right-aligned. A running subagent's progress shines like the tile's live tool row; queued and waiting ones hold still. Hovering brightens the text and shows the chat's subagent hover card; clicking opens the subagent thread. At most three lines show; the rest fold into a "+N more subagents" line that opens the session. With Vim on, Tab reaches the heading's PR link, the tile, and these footer lines in that order, and Enter clicks them (`activateModalItem` falls back to a focused button or link inside the surface). Lines leave once the subagent settles. The fixed-height heading keeps cards and subagent footers aligned across a grid row.
- Switching between the overview and a session is one view transition (`useFlowOverviewTransition` in `FlowOverviewBoundary`, so every entry point gets it: tile, Flow bar, sidebar, `w g`, Escape, advancing, toggling Flow): the session's tile grows into the chat pane and shrinks back into it on return (which puts the grid cursor on that tile), a waiting session's favicon and title fly to and from its Flow bar card, and the rest crossfades (~240ms; a plain crossfade when the session has no tile; instant under reduced motion or without the View Transitions API). Entering holds the overview (up to 400ms) until the route reaches the opened session, so the previous route's chat doesn't flash.
- Enabling Flow hides the sidebar; after that the sidebar can be toggled freely and disabling Flow leaves it as is.
- While the Flow bar shows, `mod+1`–`mod+9` open that waiting session in Flow bar order, whatever area has focus; an empty slot falls back to the sidebar's thread. There are no `gt`/`gT` session motions.
- Successful user actions (send, answering approvals/input, settle, snooze, archive, implement plan) advance to the first eligible important waiting session, otherwise the oldest eligible ordinary waiting session, or back to the overview when none remain. Destination selection reads the latest flags after the action succeeds; running, snoozed, disconnected, current, and explicitly excluded sessions are not destinations.
- Never pull the user anywhere on background activity alone. Typing, navigating, or leaving Flow cancels a pending jump; automatic queued sends never navigate.

## Hermes provider

Hermes is a selectable ACP provider with settings, icon, model discovery/switching, session resume, and recovery after cancellation. See [Hermes setup and limitations](docs/user/install.md#hermes).

- A configured instance is usable without a warning while credentials are unverified, including after restart. Missing credentials and failed turns still warn; routine refreshes don't clear a failed-turn warning. Status checks never send model requests.
- Model labels keep an inference-route suffix so identical model names from different routes stay distinguishable.
- Agent profile is chosen per conversation (always explicit, defaulting to `default`; no "automatic"), preserved through drafts, sends, and resume on all clients. Switching profiles starts a fresh session (seeded with upstream's thread-summary handoff); never load another profile's session.
- Reasoning effort is session-scoped, applied before the next prompt, survives resume, never writes profile config, and errors clearly on Hermes versions that can't honor it.
- Each instance's Hermes home isolates its config, credentials, memory, and skills. Report capabilities honestly.
- The composer's slash menu lists the commands Hermes advertises over ACP (`available_commands_update`). ## Lexicon figures

An agent can show a Lexicon figure, an interactive board of the model items it is discussing, as an `html_render` page in any provider's thread. Lexicon writes the page (`lexicon_figure` in the Lexicon repo) and serves its script; Hydrogen supplies three generic render changes. Each carries an inline comment: if upstream ships an equivalent, take upstream's version on merge and drop ours.

- **`path` input.** `html_render` and `html_preview` take either `html` or `path`, an absolute path to a local file read once at publish and stored like an inline page (same 512,000-character cap and local-image inlining). The file must be an HTML document (doctype or `<html>` after BOM, whitespace, comments), so a symlink or renamed file cannot carry a secret into a page or a preview screenshot. Coverage: [`HtmlRender.test.ts`](apps/server/src/htmlRender/HtmlRender.test.ts).
- **Render links follow "Open links in".** On web and desktop, a link clicked in a render (inline or opened in the file panel) opens through `useOpenLink` beside the render's thread; the bootstrap forwards the click's Cmd/Ctrl so a modifier click reaches the system browser. Mobile keeps opening them in the system browser. Seam: [`BrowserDocumentFrame.tsx`](apps/web/src/components/files/BrowserDocumentFrame.tsx).
- **Escape hatch.** The bootstrap reports an Escape the page left alone (seen in the capture phase, so stopping propagation doesn't hide it; checked after dispatch) as `t3/notifications/unhandled-escape`; the client releases focus from the focused frame (see Vim navigation). Pages published earlier lack it. Coverage: [`htmlRender.test.ts`](packages/shared/src/htmlRender.test.ts).

Verify in a real client: a Lexicon figure's links open in the browser panel, Escape returns from the figure, and `Enter` enters it in Vim mode.

## Expanded shell commands

Web and desktop automatically format unfolded shell tool calls into readable lines: command chains and pipelines break at syntax boundaries, and conditional/loop bodies indent. Quoted shell launcher scripts (such as `bash -lc`) receive the same layout. Syntax highlighting continues to recognize embedded languages.

- Formatting loads only when a command is unfolded. Quotes, escapes, comments, and heredoc contents survive; invalid, non-Bash, or oversized commands retain their original layout.
- A **Copy original command** button copies the original input, independent of display formatting. Execution, stored tool input, and native mobile behavior stay unchanged.
- Mouse disclosure and Vim tool-call expansion use the same renderer, for standalone calls and calls inside groups. Coverage: [`shellCommandFormat.test.ts`](apps/web/src/customizations/huy/shellCommandFormat.test.ts).

## Diff repository identity

The diff panel shows the selected thread's own repository/worktree. If that workspace is unavailable, show the error; never fall back to the server's working directory and show another repo's diff. Review requests are accepted for registered projects outside the server's startup directory.

Web and desktop remember each thread's last diff scope (Changes, turn, or Worktree) when navigating back, reopening the panel through tabs, commands or shortcuts, and opening it automatically after a turn completes. Threads without a saved selection default to Changes; a timeline diff action still selects its requested turn/file. Prefer an equivalent upstream main fix when merging. Selection coverage: [`diffPanelStore.test.ts`](apps/web/src/diffPanelStore.test.ts); opening paths: [`ChatView.tsx`](apps/web/src/components/ChatView.tsx).

## Thread worktree attach

Agents can re-point their own thread at an existing checkout of its project with the `t3_worktree_attach` MCP tool: a linked worktree (for example one created with shell `git worktree add`, or after the thread started in the wrong worktree) or the project's main workspace root. This is the agent-side counterpart of picking a branch already open in another worktree from the branch menu.

- It never runs a git command in the checkout or changes its branch. The target must be a checkout of the thread's own repository with a branch checked out, verified against the ref inventory, rescanned when the cached one misses a just-created worktree.
- Re-attaching to the current binding is a no-op that keeps the session. Otherwise the binding change detaches the session like `t3_worktree_handoff`, and `continuationPrompt` resumes in the new checkout.
- Upstream has `t3_worktree_handoff` (new worktree only). If upstream main ships an equivalent attach, favor upstream's implementation when merging and remove this one. Coverage: [`WorktreeMcpService.test.ts`](apps/server/src/mcp/WorktreeMcpService.test.ts).
